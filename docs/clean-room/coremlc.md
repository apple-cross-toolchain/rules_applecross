# coremlc

Reproduced: `coremlc compile` and `coremlc generate` of ML Programs
(`.mlpackage`, with states, several functions, flexible shapes, optional
inputs, images among their inputs and outputs, and compressed weights), and
of every other model type of the published specification but neural
networks (`.mlmodel`): tree ensembles, support vector machines, linear
models, Bayesian probit regressors, k-nearest neighbors classifiers
(updatable ones too), item similarity recommenders, the feature transforms,
non-maximum suppression, class confidence thresholding, custom and linked
models, Vision and audio feature prints and sound analysis preprocessing,
pipelines of any of these, and Create ML's text classifiers, word taggers,
gazetteers, word embeddings, recommenders, and tabular, image and sound
classifiers; as rules_apple runs them. Compiling writes
`<Name>.mlmodelc/` and the partial Info.plist. Generating writes the Swift class
(`--public-access --language Swift`) or the Objective-C pair. The
implementation is `toolchain/stubs/coremlc.py`, pure Python, with its
operation table in `coremlc_ops.json`.

Provenance: black-box, as [README.md](README.md) describes. Sources:
- the outputs of Xcode 27.0's `coremlc` (Core ML compiler 3600.25.1, MIL
  component 3600.16.1) for models made for the purpose;
- its usage messages.
- Apple's published Core ML model specification (the protobuf schema
  coremltools ships), for reading models, and its comments, for what to
  probe.
- coremltools (its MIL builder and converter, its multi-function and weight
  compression utilities), to build the test models and to list MIL operation
  names; its published MIL operation definitions (the compression operations'
  inputs) and its packing of integers narrower than a byte, to read models.
- Apple's public CreateML framework, from small Swift programs, to train text
  classifiers, word taggers, tabular models, image classifiers, gazetteers,
  word embeddings, recommenders, sound classifiers (on generated tones and
  noise), activity classifiers, object detectors and style transfers as
  Create ML exports them (the images drawn for the purpose).
- coremltools's k-nearest neighbors builder, for updatable models; the other
  `.mlmodel` probes were written with the specification's protobuf
  messages.
- CoreFoundation's published string hash and hash tables, for key order.

Generating writes Xcode's fixed template text, taken from its outputs, around
what comes from each model. No Apple binary was read.

Method: about 290 ML Programs, built with coremltools's MIL builder, were
compiled and generated by Xcode and by this tool:
- 80 written to isolate one behaviour each (feature types, classifiers,
  names, deployment targets, control flow, weights);
- 201 random programs of up to eight of 100 operations, across iOS 15–18
  targets and both precisions.

Every compiled file matched (allowing Xcode's random map order, below), and
so did every generated Swift and Objective-C file.

1,382 more were made for the features below (states, optional inputs,
images, several functions, flexible shapes, operations, compressed weights,
lists, constants and metadata):
- 1,342 compile as Xcode compiles them, and the 40 that Xcode refuses are
  refused too;
- all 1,379 that Xcode generates classes for generate the same Swift and
  Objective-C, and the 3 it refuses are refused too.

531 of them are random mixtures, made after the rules were written. Of the
first round's 350, the first 160 caught two rules (states among enumerated
shapes, Float16 arrays beside images), fixed before the next 160 were made;
those caught one (Grayscale16Half images with enumerated sizes), and the
last 30 none. The 181 made for compressed weights, `resample`, lists,
Grayscale16Half images, non-finite constants and escaped metadata caught
none.

An app built entirely on Linux (`//examples/ios/HelloWorldSwift`, with
`examples/resources/Doubler.mlpackage`) carries a compiled model and a generated class byte-identical to Xcode's.
`tests/coremlc` keeps 338 models with Xcode's output: 318 compiled, 7 that
Xcode refuses, and 268 with generated classes (the 67 `classic_*` cases
are the other `.mlmodel` types).

## Xcode's own output varies

Xcode writes a model's user-defined metadata (a protobuf map) in a randomly
seeded order. So a model with more than one entry compiles to different
`coremldata.bin` and `metadata.json` bytes on every run. coremltools adds
three entries to every model it converts.

This tool keeps the model's own order, so its output is the same on every
run. For such models it matches Xcode up to that order; for models with at
most one entry it matches byte for byte. The tests compare compiled models
with `tools/xcode_equivalence.py`, which sorts that map on both sides and
then compares the bytes, so a model's metadata is checked like the rest.
Every probe for the features below was compiled twice by Xcode; no other
output varied, compressed weights included.

A model compiled to its own specification (below) is the specification as
Xcode re-encodes it, so its other maps vary from run to run too: a custom
model's parameters and a categorical mapping's map. `xcode_equivalence.py`
sorts those as well (and an imputer's dictionary, which is refused).
Xcode also writes uninitialized bytes into `_B0000.DAT` for an item
similarity recommender without items; that is refused.

## Compiled files

- **`model.mil`** is the program printed as text:
  - `program(1.0)`, or `program(1.3)` from specification 9, where rank-0
    tensors are written as their element type;
  - the `buildInfo` gains coremlc's own two entries (a program without one
    gets just those);
  - functions, function inputs, operation inputs and attributes are
    sorted;
  - floats are written as C's `%a` writes them, except that infinities are
    `inf` and `-inf` and every NaN, whatever its sign or payload, `nan`;
  - byte-packed integers are written in decimal, those narrower than a
    byte (`int4`, `uint1`–`uint6`) unpacked from each byte's least
    significant bit up, and an unknown dimension as `?`;
  - a list's type is `list<tensor<fp32, [2, 3]>, 2>`, its length `?` when
    unknown;
  - a variadic input is written `(a, b)`, an input bound to a value as the
    value, and several outputs `type a, type b = op(...)`;
  - a name declared more than once in a function is numbered by
    occurrence (`name_0`, `name_1`), its references within its scope too;
  - coremlc gives a function the attributes its description implies:
    default values and flexible shapes (below);
  - a classifier's `classify` is left out, its function returning the
    probabilities instead.
- **`weights/`** is copied from the package as it is, compressed weights
  included.
- **`coremldata.bin`** is a small archive:
  - u32 502, then a version (5 for specifications 6 and 7, otherwise the specification);
  - 20 zero bytes, then the length-prefixed tag `generic` and the specification version;
  - 28 zero bytes, then the length-prefixed model description (the model's own bytes);
  - then u32 502 and 12 zero bytes, once per function.

  A description without metadata is written with an empty one.

  A classifier ends instead with:
  - u32 403 and u32 0;
  - the label type (100 for strings, 101 for 64-bit integers), the label count and the labels;
  - the length-prefixed name of the probabilities output;
  - eight zero bytes.
- **`analytics/coremldata.bin`** holds sections of length-prefixed keys and
  values, with `modelHash` the base64 of the source model's SHA-256.
- **`metadata.json`** is NSJSONSerialization's pretty printing of a
  CoreFoundation dictionary, enumerated in CFBasicHash's order:
  - Keys go in in coremlc's order, fitted to every observation; operations are counted in first-use order.
  - `computePrecision` lists what the operations produce, constants included (a list counts its elements' type), but not the function's inputs; bool and string don't count.
  - `storagePrecision` gives the type of the weight-file constants some
    operation reads and of the weight-file values bound to other operations'
    inputs, and the compression operations' own descriptions (below);
    several are `Mixed (Float32, Int8)`, sorted as strings.
  - Strings are escaped as NSJSONSerialization escapes them: `\"`, `\\`,
    `\/`, `\b`, `\f`, `\n`, `\r`, `\t`, and other control characters
    `\u001f`.
  - `mlProgramOperationTypeHistogram` names each operation:
    - CamelCase (`Relu`) for iOS 15;
    - otherwise `Ios<N>.<camelCase>`, with N the newest of Apple's versions of it that isn't above the target.

    The table of 165 operations comes from compiling each one for each
    target; an entry that lists targets was established for those alone.
- **The partial Info.plist** sets `LSBundleContainsCoreMLmlmodelc`.

## States

Stateful models (specification 9; `StateTensorSpec`, `read_state`,
`coreml_update_state`):
- `model.mil` gives a state input as `state<tensor<fp16, [2, 3]>> k`, and
  writes `write_state(data = v, input = k)[...]`, which declares nothing;
- the description, states included, is copied into `coremldata.bin`;
- `metadata.json` lists them under `stateSchema`, as `State`, with a
  `formattedType` of `State (Float16 2 × 3)` and no `hasShapeFlexibility`;
- the generated classes gain a state class (Swift `XState`, its `Name`
  enumeration naming each state; Objective-C `XStateName` and `XState`),
  `makeState()` (`newState`), and predictions taking the state
  (`using state:`, `usingState:`); there are no batch predictions.

16 models (ranks 1–5, up to three states, keyword names, descriptions,
`slice_update`, an image input, Float32 computation), 2 with several
functions and 93 random mixtures compared: all matched.

## Optional inputs and default values

A `TensorType` with a `default_value` is an optional input with a default
(`floatDefaultValue`, or `intDefaultValue` for an Int32 array):
- `model.mil`'s function gets `CoreML_InputDefaultValues`, a dictionary of
  each optional input's default as a float (`%.9g`; 0 when none is given);
- `metadata.json` marks it `isOptional` and its `formattedType` ends in `?`;
- Swift makes it optional (`MLMultiArray? = nil`), and initializers and
  predictions take optional inputs last; Objective-C makes it `nullable` and
  adds an initializer without it.

Xcode refuses a default of another type than its array's, and a model whose
inputs are all optional; so does this tool. 28 models (iOS 15–18, ranks 1–5,
Float16, Int32, odd values, first, middle, keyword-named, beside an image or
a flexible shape), 2 with several functions and 36 random mixtures
compared: all matched.

## Flexible shapes

`RangeDim` and `EnumeratedShapes` inputs, of multi-arrays and images:
- the program has `?` for each flexible dimension, and coremlc gives the
  function `FlexibleShapeInformation`: each flexible input's default shape,
  and either each one's ranges (`RangeDims`) or every enumerated
  combination of all the inputs' and states' shapes (`EnumeratedShapes`).
  A combination is named for those shapes, padded to rank 5
  (`x_1_1_1_2_3_`), from specification 9 by that name's SHA-256 (eight hex
  digits). Several inputs' enumerated shapes (iOS 18) combine by position;
- `metadata.json` adds `shapeRange` (`[[1, 4], [2, 2]]`) or
  `enumeratedShapes`, and `shapeFlexibility` (`1...4 × 2`, `3 × 3 | 1 × 2`);
  an image adds `sizeRange` or `enumeratedSizes` (width first) and
  `sizeFlexibility`. A flexible multi-array's keys go in in an order of
  their own;
- an output without a fixed shape is `MultiArray (Float32)`, shape `[]`.

Xcode refuses a model mixing ranges and enumerated shapes. 39 written to
vary one thing (ranks 1–5, ranges, enumerated sets, defaults, Float16,
Int32, iOS 15–18), 113 random ones, 19 more written for images, several
functions and edge cases, and 130 random mixtures compared: all matched.

## Images

Images among other inputs: Swift's initializers from a `CGImage` or a URL
take every input (arrays as `MLMultiArray`, then as `MLShapedArray`), and
Objective-C's name each image `xFromCGImage:` or `xAtURL:` (later ones
`yCGImage:`, `yAtURL:`). Images can be outputs (`CVPixelBufferRef`,
released in `dealloc`), non-square (`Image (Color 10 × 6)`, width first),
or Grayscale16Half (`kCVPixelFormatType_OneComponent16Half`). An API with a
Float16 `MLShapedArray` is unavailable on Intel Macs (`#if ... arch(x86_64)`)
and, before specification 9, needs macOS 15.

Enumerated sizes: at specification 7 Xcode gives a Grayscale16Half image's
enumerated shapes three channels (`img_1_1_3_4_6_`, `[1, 3, 4, 6]`) while its
default keeps one; at specification 8 and 9, and for other images, they
keep their own. Xcode refuses any image with enumerated sizes whose program
input fixes its height or width ("has a different shape than its
corresponding parameter to main"), whatever its color space or target; so
does this tool. Size ranges with a fixed dimension compile.

30 written for these, 8 edge cases and 180 random mixtures compared, then 26
more written for enumerated sizes and 30 among the compressed weights'
mixtures: all matched. They showed that `left` and `right` get a trailing
`_`, as the keywords under Generated code do.

## Multiple functions

`save_multifunction` models (description field 20, `defaultFunctionName`):
- `model.mil` lists every function, numbering repeated names within each;
- `coremldata.bin` ends with one u32 502 and 12 zero bytes per function;
- `metadata.json` describes the default function at the top and each
  function under `functions` (its schemas, histogram and precisions), with
  `defaultFunctionName`;
- the generated classes are the default function's.

18 written for this (states, images, weights shared or not, flexible and
optional inputs, defaults first or not) and 30 random ones from the
mixtures compared: all matched, byte for byte.

## Operations and compressed weights

53 operations were added in the first round: 50 that coremltools offers,
each compiled alone for every target it has (183 models),
`constexpr_blockwise_shift_scale` from compressed models, and `read_state`
and `write_state` from the states. Xcode doesn't know `conv_quantized`. This
round added the list operations and iOS 18's `constexpr_lut_to_sparse` and
`constexpr_sparse_blockwise_shift_scale`, extended `resample` and
`constexpr_cast` to every target, and leaves no operation coremltools
offers out of the table but `conv_quantized`.

**`resample`.** From iOS 16 coremlc gives it two more inputs, written as
values: `coordinates_format = "xy"` and `coordinates_type = "absolute"`,
whatever its modes, its coordinates (a constant or an input) and its
precision. Xcode refuses a mode it doesn't know (`coordinates_mode =
"scaled"`); this tool accepts only the modes seen compiled (three coordinate
modes, four padding modes, bilinear and nearest sampling), on iOS 15 too.

**Lists** (`make_list`, `list_write`, `list_read`, `list_gather`,
`list_scatter`, `list_length`, within `while_loop` and `cond` too) are named
`MakeList`, `ListWrite` and so on in the histogram on every target, and
`computePrecision` counts their elements' type even when nothing is written
to them. coremltools writes list and tuple values only for a classifier's
classes (left out of `model.mil`) and custom layers (unknown operations),
so those values are still refused.

**Compressed weights.** Everything coremltools 9's
`coremltools.optimize.coreml` makes for iOS 16–18 compiles as Xcode
compiles it: palettization (1–8 bits, per tensor or per grouped channel,
along either axis, with per-channel scales), pruning (threshold, magnitude,
block and n:m), linear quantization (Int8, UInt8, Int4 and UInt4, per
tensor, channel or block) and their joint forms (pruned and palettized,
pruned and quantized, palettized with a quantized table, and all three).
The weights file is copied as it is; `model.mil` prints the operations as
any other, and `metadata.json` describes them in `storagePrecision`:
- iOS 16's operations hold their weights as attributes, whose types don't
  count; each adds its own description instead:
  - `constexpr_lut_to_dense`, `Palettized (N bits)`;
  - `constexpr_sparse_to_dense`, `Sparse`;
  - `constexpr_affine_dequantize`, its quantized data's type (`Int8`,
    `UInt8`), even when held as a value rather than in the weights file;
  - `constexpr_cast`, nothing.
- iOS 18's take their weights as inputs; those from the weights file count
  their type (`UInt2` indices, `UInt1` masks, a `Float16` table, `Int4`
  data), values in the model itself don't, and each adds its description:
  - `constexpr_lut_to_dense`, `Palettized (N bits)`;
  - `constexpr_sparse_to_dense`, `Sparse`;
  - `constexpr_blockwise_shift_scale`, its data's type, however held (a
    value, or another operation's output);
  - `constexpr_lut_to_sparse`, `constexpr_sparse_blockwise_shift_scale`
    and `constexpr_cast`, nothing.
- N is the bits that would index every entry of the lookup table, all its
  groups and vector elements together: the table's element count rounded
  up to a power of two (`[4, 1, 16, 1]` is 6 bits, `[3, 1, 4, 1]` 4,
  `[1, 1, 2, 3]` 3, a table another operation makes by its type). Several
  sizes sort as strings: `Palettized (10 bits)` before `Palettized (9
  bits)`.
- An operation's description counts whether or not anything reads its
  output.

The operations were probed one variation at a time (108 models: index widths
1–8, tables of 2–1,024 entries in groups, vectors and other operations'
outputs, indices, masks, tables and data in the weights file or as values,
Float16, Int8 and UInt8 tables and data, outputs only returned, every
target), coremltools's compression run as users run it (96 models, iOS
16–18, both precisions), and the first round's 38. Probes for `resample`
(46), lists (40), Grayscale16Half and other images (26), non-finite and
64-bit constants (24) and escaped names and metadata (34) came with them; 181
random mixtures of all these followed, after the rules were written.

## Text classifiers and word taggers

Their `coremldata.bin` has its own header, followed by the model's whole
specification:
- u32 2000 (text classifier) or 2001 (word tagger), the model's field number;
- u32 1 and 20 zero bytes;
- the length-prefixed tag `spec`, then the specification version (3);
- 28 zero bytes.

Xcode re-encodes the specification, so a model whose user-defined metadata
has more than one entry varies from run to run here too.

Their analytics hold only `SpecificationDetails`. `metadata.json` has the
class labels (`stringClassLabels`, or a word tagger's `stringTags`) and the
model type, and no operation histogram or precision. Sequence features
(`Sequence (String 0...10000)`) give `valueType` and `sizeRange`.

Generated code for specification 3 follows Xcode's template of that era:
- a deprecated `init()`, and no default configuration;
- iOS 14 and 15 availability on loading;
- iOS 17 availability on asynchronous prediction;
- sequences as `[String]`, or `[Int64]` passed as `[NSNumber]`;
- in Objective-C, sequences as `NSArray`.

Twelve models compared, trained with five label sets and the possible
metadata. Every compiled and generated file matched, up to Xcode's map order
for the one with two metadata entries.

## Tabular models

Create ML's linear and logistic regression models (`MLLinearRegressor`,
`MLLogisticRegressionClassifier`, and the `MLRegressor` and `MLClassifier`
that pick them) are pipelines (specification 1) of one-hot encoders, a
feature vectorizer and a linear model. Compiling one writes a directory per
part, `model0/`, `model1/` and so on:
- each part's `coremldata.bin` has the text classifiers' header, with the
  part's own field number (300 linear regressor, 400 linear classifier, 600
  one-hot encoder, 602 feature vectorizer) and specification version, then
  the part's bytes;
- the top `coremldata.bin` has u32 200 (classifier) or 201 (regressor), u32 1
  and 12 zero bytes, u32 1 and u32 0, the length-prefixed tag
  `generic.model0v1.0.0spec.model1v1.0.0spec…`, the specification version
  and 28 zero bytes, then the length-prefixed model description, the part
  count, and u64 200 or 201 again.

Their analytics add `PipelineModelDetails` (the part count). `metadata.json`
names each part under `modelType`, and a classifier's labels come from its
linear model (`stringClassLabels` or `int64ClassLabels`). Number features
are `Double`.

Generated code for specification 1 follows the specification 3 template,
with availability from iOS 11, and iOS 12 availability on the configuration
initializers and on batch predictions.

Fifteen models compared, trained with five feature and label sets and three
kinds of metadata, and four more from earlier probes. Every compiled and
generated file matched, up to Xcode's map order for the two with two
metadata entries.

## Tree ensembles

Tree ensembles (`treeEnsembleRegressor` and `treeEnsembleClassifier`) come
on their own, from coremltools's converters, or as the last part of Create
ML's boosted tree, random forest and decision tree pipelines. Either way
they compile to a `coremldata.bin` and a `_B0000.DAT` (in a pipeline,
`model<N>/`, its tag `model<N>v1.0.0generic`).

`coremldata.bin` has the `generic` header (u32 302 or 402, the specification
version as given), the model description re-encoded (fields in number
order, empty strings dropped, empty metadata always written), then u64 0,
the length-prefixed name `_B0000.DAT` and the number of prediction
dimensions. A classifier adds its string labels and its integer labels,
each counted (one of the two empty). On its own, the model's analytics hold
only `SpecificationDetails`.

`_B0000.DAT` is the trees in a packed form (little-endian):
- the base prediction, to which every tree that is only a leaf is added
  (in tree id order) and then dropped;
- a 12-byte header of field widths: record size, feature index, flags,
  child, record count, dimension and sparse index, and a code for the
  comparisons used;
- one record per branch node, in preorder, true child first: the feature
  index, two leaf flags, the missing-value flag and the comparison (a
  negation bit, or the comparison itself when they're mixed or equality),
  then the false child's offset or the leaf's number, then the threshold.
  A branch whose only leaf child is the true one is written swapped, its
  comparison negated and its missing-value flag inverted;
- each tree's root, the leaves' values (dense; sparse when few leaves have
  a value for every dimension; or one value per leaf) and offsets, in
  packed arrays of the narrowest width that holds them;
- the post-evaluation transform.

Values are float32 unless some threshold or leaf value isn't exactly a
float32, when all are float64.

The layout was fitted to 479 models built to vary one thing each (tree
counts and depths, node and tree ids, every comparison, missing-value
flags, feature indices, dimensions, base values, leaf values, transforms,
string and integer labels), then checked against 180 random ensembles made
afterwards. Those caught one rule (when values go sparse), fixed before the
last 100 were made. [coremlc-trees/](coremlc-trees/README.md) has every rule
with the probes that establish it, and the scripts that make them. All 714 compiled models match, the 48 Create ML
pipelines (boosted trees, random forests, decision trees, classifiers and
regressors) included, as do the generated classes of those 48 and of 96
others. Compiling the same model twice gives the same bytes.

Not reproduced: updatable trees, transforms other than the four the
specification defines, trees that aren't well formed (no single root,
unreachable or missing nodes), and descriptions whose features' own
fields are out of order.

## Image classifiers

Create ML's image classifiers are pipeline classifiers of a Vision scene
print (field 2002) and a linear classifier, at specification 3 (scene print
revision 1) or 8 (revision 2). They compile as the tabular pipelines do, the
scene print a part like the others. Xcode treats them as their own kind:
- `metadata.json` names the model type `MLModelType_imageClassifier`, and its
  availability gives watchOS as `unavailable`;
- the generated classes say `@available(watchOS, unavailable)` (Objective-C:
  `API_UNAVAILABLE(watchos)`) in place of a watchOS version;
- before specification 4, the image conveniences (from a `CGImage` or a URL)
  are marked iOS 13.

Before specification 6, the `MLShapedArray` conveniences are marked iOS 15.

Nine models compared: two and three classes, labels with spaces and
non-ASCII letters, both revisions, specification 1 as well, with and without
metadata. Every compiled and generated file matched. Other models with a
feature print are under Other model types, below.

## Other model types

Every other model type of the published specification but neural networks
compiles too, on its own or as a pipeline's part, and generates its
classes. 935 models were written for them with the specification's
protobuf messages, each to vary one thing, and compiled twice and generated
by Xcode and by this tool:
- of the 687 Xcode compiles, 674 compile the same (up to the maps above) and
  13 are refused here (below);
- the 248 Xcode refuses are refused too;
- every generated Swift and Objective-C file of those matches, but for the
  13 and 11 more that are refused (optional images, names that need
  escaping, and a serialized model, whose classes Xcode generates though it
  doesn't compile it).

### Models compiled to their specification

Most types compile as text classifiers do: `coremldata.bin` is a header
(u32 the model's field number, u32 1, 20 zero bytes, the tag `spec`, the
specification version, 28 zero bytes) and the whole specification, a
description without metadata given an empty one. Their analytics hold only
`SpecificationDetails`, and `metadata.json` names the type
(`MLModelType_supportVectorRegressor` and so on). So compile:
- `supportVectorRegressor`, `supportVectorClassifier` (every kernel, dense
  and sparse support vectors), `glmRegressor`, `glmClassifier`,
  `bayesianProbitRegressor`;
- `identity`, `normalizer`, `scaler`, `imputer`, `arrayFeatureExtractor`,
  `categoricalMapping`, `dictVectorizer`, `oneHotEncoder`,
  `featureVectorizer`;
- `nonMaximumSuppression`, `classConfidenceThresholding`, `customModel`,
  `linkedModel`;
- `visionFeaturePrint` (scenes, revisions 1 and 2, and objects),
  `audioFeaturePrint`, `soundAnalysisPreprocessing`, `gazetteer` and
  `wordEmbedding`.

`metadata.json` adds:
- a classifier's labels (`classLabels`), each once, in the order first
  given; a gazetteer's from its own label field;
- for a custom model, `customModels` (its class name and description);
- for a linked model, `modelParameters`: `linkedModelFileName` and
  `linkedModelSearchPath`, each with its default (empty when not given),
  `scope` and `dataType` `String`;
- for any model using a Vision feature print, standalone or in a pipeline,
  `watchOS` `unavailable` in its availability (and in the generated
  classes, as for image classifiers).

Xcode refuses `serializedModel` ("No known class for compiling"); so does
this tool, which doesn't generate its classes either.

### Checks

Xcode checks a model as it reads it, for compiling and generating alike,
and refuses one that fails. 404 models were written to break one rule each;
155 of them Xcode refuses. This tool makes the same checks, and refuses any
form of model it hasn't seen accepted:
- every model: at least one input and one output, each named and typed; an
  input array with a shape; Float16 arrays and Grayscale16Half images from
  specification 7, sequences from specification 3; no optional outputs,
  and optional inputs only to an identity, an imputer and an item
  similarity recommender; a default shape within its ranges;
- regressors and classifiers: a predicted feature that is an output, of the
  labels' type; classifiers' labels;
- GLMs: as many offsets as weights; with reference-class encoding one
  weight vector fewer than classes; one-vs-rest, one per class, or one for
  two classes; transforms and encodings the specification defines;
- support vector machines: a kernel, support vectors, as many coefficients
  as support vectors; for a classifier, support vectors per class adding up,
  one coefficient vector fewer than classes, as many `probA` as `probB`;
- normalizers, scalers, imputers, array feature extractors, categorical
  mappings, one-hot encoders and dictionary vectorizers: one input and one
  output of the types Xcode accepts (a dictionary vectorizer's output is a
  dictionary: Xcode refuses an array), their parameters given and of the
  types of their features;
- non-maximum suppression: its named features present, Double arrays, the
  outputs exactly those it names, thresholds between 0 and 1, as many
  labels as the confidence output's classes;
- class confidence thresholding: curves, each of non-empty components of
  one length; custom models a class name; linked models a file name;
- feature prints: one image (or audio array) in, a known kind and version;
  object prints two named outputs; gazetteers and word embeddings revision
  2 or later, their data and a string input.

### Specification versions

Every type compiles at the specifications Xcode accepts it at, 1 to 10
(the last iOS 19 and its contemporaries). Generated classes follow:
- specification 2: availability macOS 10.13.2, iOS 11.2, watchOS 4.2, tvOS
  11.2;
- specifications 2 to 4: the specification 3 template;
- specification 5: that template without the deprecated `init()`, with a
  default configuration, and with loading by completion handler unmarked;
- specification 10: availability macOS 16, iOS 19, tvOS 19, watchOS 12,
  visionOS 3.

30 models (three types at each of specifications 1 to 10) compared.

### Features

- A sequence without a size range is `Sequence (String 0)`, `[0, 0]`; an
  upper bound of -1 is unbounded (`0...`, `[0, -1]`); equal bounds are
  written once.
- Any input may be optional where the type allows it: its formatted type
  ends in `?`; Swift makes it optional; Objective-C makes it `nullable`, an
  integer or double an `NSNumber`. Without required inputs, Objective-C has
  no initializer leaving optional ones out.
- An input dictionary's value in Swift is `try! MLFeatureValue(dictionary:
  x as [NSObject : NSNumber])` (`try!` first when optional).

168 models (every feature type, optional or not, sequences, flexible shapes
at specifications 1 to 4, names and descriptions) compared.

### k-nearest neighbors

`kNearestNeighborsClassifier` compiles to its own archive, tagged
`notreesyet`: after the usual header and the description (canonical, as
the trees' is), u32 the dimensions; u64 the count and the samples as
float32; the labels (u64 0 when not given, else u64 100 or 101, the count
and the labels as given, repeats kept); the default label (u64 0, or u64 110
and a string, or u64 111 and an int64); u32 the weighting (0 uniform, 1
inverse distance), u32 the index (0 linear, 1 k-d tree, then u32 its leaf
size); labels given empty are u64 100 (or 101) and a count of 0.
`modelParameters/coremldata.bin` is u64 0 and
`modelParameters/numberOfNeighbors/coremldata.bin` the `Int64Parameter`'s
own bytes; `metadata.json` describes it under `modelParameters` (default,
`allowedRange` or `allowedSet`, `scope`). The labels in `metadata.json` are
each given once.

Xcode refuses: no index, distance or weighting; a leaf size that isn't
positive; a sample of another length than the dimensions; labels not one
per sample; no labels and no default; a default of another type; a number
of neighbors not positive, out of its range or set. So does this tool. 60
models compared, 18 of them refused by both.

Updatable ones, as coremltools's builder makes them (specification 4 or
later; training inputs the model's own features): `metadata.json` says
`isUpdatable` `1`, with `updateParameters` (none) and `trainingInputSchema`;
`updateParameters/coremldata.bin` is u64 0; the generated classes gain a
`<Name>TrainingInput` class ("Model Update Input Type"), shaped as the
input class, after the output class. Xcode refuses other updatable types
("not supported for on-device update"). 9 compared.

### Item similarity recommenders

`itemSimilarityRecommender` compiles to the `generic` archive and a
`_B0000.DAT`: after the description, u64 0, `_B0000.DAT`, u64 the item
count (the ids' if given, else the largest item plus one), the integer ids
and the string ids (each counted), and the six feature names. The data
file holds the similarities as a sparse matrix, in the trees' packed
arrays:
- u32 0, u32 the largest item plus one, u64 0;
- the row offsets: one per row up to the last listed one, an unlisted item
  before a listed one repeating the offset reached, one short of a row each;
- each row's columns, sorted, the first as it is and the rest as the gap
  from the one before less one; zero scores are left out;
- u64 the count and the scores as float64;
- the score adjustments: u64 0 when none are given, else u64 the item count
  and one per item (0 when not given).

Xcode refuses ids of both kinds, repeated string ids, and fewer ids than
items: integer ids must cover every item, string ids all but the last.
Items listed twice or with a similar item twice (Xcode sums their scores)
are refused here, and so is a recommender without items. 122 models
compared, 30 of them refused by both.

### Pipelines

Pipelines (`pipeline`, `pipelineClassifier`, `pipelineRegressor`) of any of
these parts compile as Create ML's tabular models do, at any specification
Xcode accepts. Also:
- a pipeline part compiles to its own pipeline archive in `model<N>/` (its
  tag in the parent's `model<N>v1.0.1generic.…`), with analytics of only
  `PipelineModelDetails` and no `metadata.json`; `metadata.json` nests its
  structure;
- k-nearest neighbors parts are tagged `notreesyet`, item similarity ones
  `generic`;
- a part (a pipeline too) keeps its description as given, without an empty
  metadata added;
- names given to the parts go in `modelNames/coremldata.bin` (u64 the
  count and the names), and scope their model parameters (`model<N>` when
  unnamed, joined with `.` within nested pipelines);
- the labels are those of the classifier giving the pipeline's predicted
  feature, else of its only classifier (nested ones count); with several,
  none.

Xcode refuses a pipeline without models, names not one per model, a part's
input that no earlier part or pipeline input gives, of another type, and a
pipeline output nothing gives; so does this tool. 78 models compared, 9 of
them refused by both.

### Create ML's other models

Trained as Create ML exports them: gazetteers (`MLGazetteer`) and word
embeddings (`MLWordEmbedding`) compile to their specification; recommenders
(`MLRecommender`, string and integer items, with ratings or not) are item
similarity recommenders; sound classifiers (`MLSoundClassifier`) are
pipeline classifiers of an audio feature print and a GLM classifier. Eight
compared. `MLActivityClassifier` and `MLStyleTransfer` export neural
networks, and `MLObjectDetector` a pipeline of a neural network and
non-maximum suppression; those are refused, as other neural networks.
`MLHandPoseClassifier` wasn't tried.

### Holdout

900 random models of all these types, pipelines nested or not, with
features, labels, specifications, metadata and occasional broken rules
drawn at random, were made after the rules were written, 300 at a time:
- the first 300 caught three rules: how many item ids Xcode requires, the
  one-vs-rest weights of two classes, and pipeline parts' descriptions
  kept as given; fixed before the next were made;
- the second caught one (a nested pipeline's description) and that the
  equivalence check didn't cover a k-nearest neighbors archive's metadata
  map;
- the third caught none.

Of the 900, 806 compile with Xcode: 802 compile and generate the same here,
4 (pipelines with an optional input, which Xcode accepts) are refused. The
94 that Xcode refuses are refused too.

## Generated code

The Swift class and the Objective-C header and implementation follow
Xcode's template:
- availability for the specification version, with the iOS 17 annotation
  on asynchronous predictions for older models;
- each feature's documentation phrase ("3 element vector of floats",
  "1 by 4 matrix", "2 × 3 × 4 3-dimensional array", images' pixel formats);
- typed accessors;
- `MLShapedArray` conveniences for arrays, and `CGImage` and URL ones for an
  image input;
- selectors whose first part capitalizes the feature's name.

A feature named after one of 96 observed keywords and identifiers (`out`,
`var`, `class`, `error`, `_Bool`, `left`, ...) gets a trailing `_`; 136 others
were seen kept as they are. An Objective-C convenience prediction whose
first input is `features` becomes `predictionFromFeatures_:`, clear of the
standard `predictionFromFeatures:`.

## Not reproduced

Refused, strict or relaxed:
- **Older neural networks** (`neuralNetwork`, `.mlmodel`), with a message to
  convert the model to an ML Program.
- **Unestablished `.mlmodel` forms:**
  - text classifiers and word taggers of specifications other than 3;
  - updatable models other than k-nearest neighbors classifiers on their
    own (an updatable pipeline's classes differ), and training inputs that
    aren't the model's own features;
  - optional inputs to a pipeline (Xcode accepts some), and optional
    images' generated classes;
  - an item similarity recommender without items (Xcode writes
    uninitialized bytes), or with an item, or an item's similar item,
    listed twice;
  - forms of a type not seen accepted: a GLM regressor's transform 3, a
    probit regressor's array output, a k-nearest neighbors classifier's
    double input, a recommender's sequence of items;
  - imputers of dictionaries and integer arrays, and other forms not seen
    accepted.
- **Unestablished ML Program features:**
  - updatable models, and classifiers with several functions;
  - list and tuple values (coremltools writes them only for classifiers'
    classes, handled, and custom layers);
  - `resample` with modes not seen compiled, or with its coordinates'
    format or type already given;
  - several inputs with enumerated shapes before iOS 18 and unbounded
    ranges (coremltools refuses to make either);
  - string constants and names needing escapes in `model.mil`
    (coremltools renames operations and features to plain names);
  - optional features other than multi-arrays;
  - compute types other than Float16, Float32, Float64, Int8, UInt8,
    Int32, UInt32, Int64, UInt16 and UInt1, storage types other than those
    and Int4, UInt2, UInt3, UInt4 and UInt6, and weights held as
    attributes of operations other than iOS 16's compression operations;
  - operations not in the table.
- **`serializedModel`**, which Xcode doesn't compile.
- **Refused by Xcode too:** the `.mlmodel` checks above, models mixing
  ranges and enumerated shapes, defaults of another type than their array,
  models whose inputs are all optional, images with enumerated sizes whose
  program input fixes their height or width, `resample` modes Xcode doesn't
  know, and operations Xcode doesn't know.

A specification is copied as it's given, where Xcode re-encodes it, so a
model not encoded as protobuf's own serializers write it would come out
different. Such a model is refused: the levels known to be messages (the
model, its description, the description's features and metadata, and the
model type's own message) must have their fields in number order, each
scalar field once and minimal varints. Two models reordered on purpose were
refused, and none of 4,578 models from coremltools, Create ML and the probes
was. (A tree ensemble is exempt: its description is re-encoded here as
Xcode does.) Deeper levels aren't checked, since without the schema their
bytes can't be told from strings and packed numbers.

# coremlc

Reproduced: `coremlc compile` and `coremlc generate` of ML Programs
(`.mlpackage`), as rules_apple runs them. Compiling writes `<Name>.mlmodelc/`
and the partial Info.plist. Generating writes the Swift class
(`--public-access --language Swift`) or the Objective-C pair. The
implementation is `toolchain/stubs/coremlc.py`, pure Python, with its
operation table in `coremlc_ops.json`.

Provenance: black-box, as [README.md](README.md) describes. Sources:
- the outputs of Xcode 27.0's `coremlc` (Core ML compiler 3600.25.1, MIL
  component 3600.16.1) for models made for the purpose;
- its usage messages.
- Apple's published Core ML model specification (the protobuf schema
  coremltools ships), for reading models.
- coremltools, to build the test models and to list MIL operation names.
- CoreFoundation's published string hash and hash tables, for key order.

Generating writes Xcode's fixed template text, taken from its outputs, around
what comes from each model. No Apple binary was read.

Method: about 290 ML Programs, built with coremltools's MIL builder, were
compiled and generated by Xcode and by this tool:
- 80 written to isolate one behaviour each (feature types, classifiers,
  names, deployment targets, control flow, weights);
- 201 random programs of up to eight of 100 operations, across iOS 15–18
  targets and both precisions.

Every compiled file matched (allowing Xcode's random map order, below), and
so did every generated Swift and Objective-C file. An app built entirely on
Linux (`//examples/ios/HelloWorldSwift`, with `examples/resources/Doubler.mlpackage`)
carries a compiled model and a generated class byte-identical to Xcode's.
`tests/coremlc` keeps 68 compile cases and 19 generate cases with Xcode's
output.

## Xcode's own output varies

Xcode writes a model's user-defined metadata (a protobuf map) in a randomly
seeded order. So a model with more than one entry compiles to different
`coremldata.bin` and `metadata.json` bytes on every run. coremltools adds
three entries to every model it converts.

This tool keeps the model's own order. For such models it matches Xcode up
to that order; for models with at most one entry it matches byte for byte.

## Compiled files

- **`model.mil`** is the program printed as text:
  - `program(1.0)`, or `program(1.3)` from specification 9, where rank-0
    tensors are written as their element type;
  - the `buildInfo` gains coremlc's own two entries;
  - functions, function inputs, operation inputs and attributes are
    sorted;
  - floats are written as C's `%a` writes them;
  - a variadic input is written `(a, b)`, and several outputs
    `type a, type b = op(...)`;
  - a name declared more than once in the program is numbered by
    occurrence (`name_0`, `name_1`), its references within its scope too;
  - a classifier's `classify` is left out, its function returning the
    probabilities instead.
- **`weights/`** is copied from the package as it is.
- **`coremldata.bin`** is a small archive:
  - u32 502, then a version (5 for specifications 6 and 7, otherwise the specification);
  - 20 zero bytes, then the length-prefixed tag `generic` and the specification version;
  - 28 zero bytes, then the length-prefixed model description (the model's own bytes);
  - then u32 502 and 12 zero bytes.

  A classifier ends instead with:
  - u32 403 and u32 0;
  - the label type (100 for strings, 101 for 64-bit integers), the label count and the labels;
  - the length-prefixed name of the probabilities output;
  - eight zero bytes.
- **`analytics/coremldata.bin`** holds sections of length-prefixed keys and
  values, with `modelHash` the base64 of the source model's SHA-256.
- **`metadata.json`** is NSJSONSerialization's pretty printing of a
  CoreFoundation dictionary, enumerated in CFBasicHash's order:
  - Keys go in in coremlc's order, fitted to every observation; operations are counted in first-use order.
  - `computePrecision` lists what the operations produce, constants included, but not the function's inputs; bool and string don't count.
  - `storagePrecision` gives the type of the weight-file constants some operation reads.
  - `mlProgramOperationTypeHistogram` names each operation:
    - CamelCase (`Relu`) for iOS 15;
    - otherwise `Ios<N>.<camelCase>`, with N the newest of Apple's versions of it that isn't above the target.

    The table of 104 operations comes from compiling each one for each target.
- **The partial Info.plist** sets `LSBundleContainsCoreMLmlmodelc`.

## Generated code

The Swift class and the Objective-C header and implementation follow
Xcode's template:
- availability for the specification version, with the iOS 17 annotation
  on asynchronous predictions for older models;
- each feature's documentation phrase ("3 element vector of floats",
  "1 by 4 matrix", "2 × 3 × 4 3-dimensional array", images' pixel formats);
- typed accessors;
- `MLShapedArray` conveniences for arrays, and `CGImage` and URL ones for an
  image input;
- selectors whose first part capitalizes the feature's name.

A feature named after one of 94 observed keywords and identifiers (`out`,
`var`, `class`, `error`, `_Bool`, ...) gets a trailing `_`; 136 others were
seen kept as they are.

## Not reproduced

Refused, strict or relaxed:
- **Older neural networks** (`neuralNetwork`, `.mlmodel`), with a message to
  convert the model to an ML Program.
- **The other `.mlmodel` types** Create ML still produces: text classifiers,
  word taggers, and the pipelines of feature vectorizers, linear models and
  tree ensembles behind tabular models and image classifiers. These are the
  next step.
- **Unestablished ML Program features:**
  - states, multiple functions, updatable models;
  - flexible shapes and default values;
  - optional inputs;
  - images among other inputs, and image outputs;
  - compute types other than Float16, Float32, Float64, Int32, Int64 and UInt16;
  - operations not in the table.
